# DALi 브라우저 포팅 계획

갱신일: 2026-10-23. 목표는 C++ DALi 코드의 브라우저 직접 렌더링과 최종적인 코드 편집·실행 환경입니다. 컴파일 서버는 사용할 수 있지만 렌더링은 브라우저에서 수행합니다.

P0 기술 검증과 R0 Public 원격 저장소 생성은 완료됐습니다. R1-a 원본·정책 선정과 R1-b 저장소 구성·검증·push가 완료됐으며 R2-a 실험 이관·Node 검증도 완료했습니다. R2-b 브라우저·Adaptor·GL 재검증과 기록 전환도 완료했습니다. P1 실행 계약 초안을 작성했으며 D1 아키텍처·D2 업로드 설계 확정, D3~D4 결정 대기입니다. [P1 설계](P1-EXECUTION-CONTRACT.md)에 근거·권장안·P2 인수인계를 기록했습니다. P1 완료와 P2 착수는 아직 승인되지 않았습니다. 나머지 단계는 계획이며 아직 구현하지 않았습니다. 초기 목표는 데스크톱, 단일 Canvas, WebGL 2, 기본 도형과 입력입니다. 이는 제안 범위이며 스레드 구조와 GL 대체 경로는 P1에서 구체화합니다. WebView·영상·카메라·다중 윈도우·네이티브 이미지 공유는 초기 범위에서 제외하는 안입니다.

D1은 P4 이후 별도 context에서 진행하는 배포 작업이며 P5의 필수 선행은 아닙니다. 공개 repo 생성은 Pages 활성화나 소스 공개 업로드까지 완료했다는 뜻이 아닙니다.

P4까지가 도형·애니메이션·입력 PoC, P6까지가 기본 UI 데모, P7까지가 웹 포팅 MVP, P9까지가 플레이그라운드 MVP입니다. P8·P9의 배포 환경과 서비스 운영 조건은 구현 전에 구체화합니다.

## 저장소 구성

대상은 [dalihub/dali-web](https://github.com/dalihub/dali-web)이며 2026-10-22에 Public 빈 저장소로 생성했습니다. 포크 3개와 submodule 대신 **단일 repo에 subtree로 소스를 포함하는 방향**을 반영합니다. 웹 포팅 변경은 dali-web에 commit하고 원본 repo에는 자동 반영하지 않습니다.

```text
dali-web/
├── libs/
│   ├── dali-core/               # subtree
│   ├── dali-adaptor/            # subtree
│   └── dali-ui/                 # subtree, foundation·components 포함
├── cmake/                      # 전체 웹 빌드 조합
├── scripts/                    # 도구 준비·빌드·upstream 설정·업데이트
├── tests/probes/               # 기존 Core·GL 검증 코드
├── tests/browser/              # 브라우저 검사
├── examples/                   # DALi 예제
├── web/                        # 정적 사이트와 실행 UI
├── services/compiler/          # P8의 외부 컴파일 서비스
├── docs/                       # PLAN·STATE·HANDOFF·JOURNAL
├── upstreams.lock.json         # 각 subtree의 원본 URL·기준 SHA·prefix
├── toolchain.lock.json         # SDK·도구 버전
└── .github/workflows/          # 검증과 Pages 배포
```

위 구조 중 libs·scripts·docs·upstreams.lock.json과 루트 README·제외 규칙은 R1-b에서 구성했습니다. R2-a에서 cmake·tests·빌드 스크립트·toolchain.lock.json도 구성했습니다. 나머지는 생성 예정입니다. services·web 등 후반 단계의 구현은 해당 단계에서 추가합니다.

1. 라이브러리 자체의 웹 이식 코드는 `libs/dali-adaptor` 등을 수정하고, 빌드 조합·사이트·예제는 상위 디렉터리에 둡니다. Core는 수정 필요가 확인될 때 변경합니다.
2. 사용자는 일반 clone으로 라이브러리 소스까지 받습니다. SDK·외부 의존 도구는 버전이 고정된 준비 절차로 별도 공급합니다. submodule 초기화나 대형 patch 적용은 요구하지 않습니다.
3. 개발자용 upstream remote는 clone으로 전파되지 않으므로 lock 파일과 설정 스크립트로 복원합니다. 사용자·CI는 일반 빌드에 이 remote가 필요하지 않습니다.
4. 원본 업데이트는 한 번에 한 subtree씩 수행하고 merge로 웹 변경과 합칩니다. 충돌 해결·회귀 검증 후 기준 SHA와 결과를 기록합니다. 공통 코드의 변경과 subtree import는 구분해서 commit합니다.
5. 최초 import와 후속 갱신 모두 `--squash`로 확정했습니다. 원본 상세 이력은 upstream에서 조회하며 full SHA·tree·ref를 lock에 보존합니다. [R1-a 결정과 근거](archive/probe/docs/R1-a-UPSTREAMS.md)를 따릅니다.
6. 사용자 후속 요청으로 세 원본을 Tizen 공식 `refs/heads/tizen`의 최신 tip으로 변경해 full SHA를 고정했습니다. Core·Adaptor는 P0와 tree가 다릅니다. 현재 Core 빌드·Node 검증은 R2-a, Firefox·Adaptor 6개 파일·GL 탐색 비교는 R2-b에서 완료했습니다. 생산 렌더러는 미검증입니다. 정확한 URL·SHA·tree는 [Tizen 기준](TIZEN-BASELINE.md)과 새 repo lock을 따릅니다. R1-a 결정은 과거 이력입니다.
7. 도구·build·프로필·대용량 로그·중첩 `.git`은 import하지 않습니다. 라이선스와 저작권 고지는 보존합니다. 최초 결과는 검토한 작은 텍스트 증거로 이관하고, 반복 실행의 큰 산출물은 CI artifact 등으로 분리합니다.
8. 원격 push와 Pages 배포는 해당 작업의 실행 지시에 포함되는지 확인합니다. R1-b에서는 명시적 허가에 따라 import·commit·push를 완료했습니다. Pages 배포는 수행하지 않았습니다.

## 이관과 서비스 배포

R2에서는 기존 `webassembly-probe`를 삭제하지 않고 필요한 소스·스크립트·문서를 새 repo로 이관합니다. `src/dali-*` 경로를 `libs/dali-*`로 바꾸고 CMake·실행 스크립트의 경로, 도구 탐색, 로그 위치를 함께 고칩니다. 기존 로컬 SDK는 재사용할 수 있지만 절대 경로를 공개 repo의 필수 조건으로 만들지 않습니다.

R2-b 이관 검증을 완료하여 `dali-web/docs`가 현재 기록 기준입니다. 기존 README·STATE·HANDOFF는 새 경로를 안내합니다. 두 곳을 동시에 최신 상태로 관리하지 않습니다. [이관 목록](MIGRATION.md)과 [R2-b 결과](R2-b-RESULTS.md)를 참고합니다.

GitHub Pages는 사전 빌드된 예제와 정적 편집·실행 UI의 호스팅 대상으로 계획합니다. 사용자 C++ 코드를 매번 컴파일하는 서비스는 P8에서 별도로 운영합니다. Actions는 SDK·예제·사이트 빌드와 배포를 담당하고, 실시간 사용자 컴파일 서버로 취급하지 않습니다.

D1 이전에 P1에서 pthreads·SharedArrayBuffer와 COOP/COEP 조건, Pages의 헤더 제약을 확인합니다. P1 초안은 pthread Worker와 별도 격리 실행 호스팅을 권장하고, non-pthread Worker 및 Service Worker를 대안으로 기록했습니다. 아직 채택·실행 검증되지 않았으며 남은 D3~D4를 확정해야 합니다. Pages 사용을 이유로 스레드 모델을 미리 확정하지 않습니다. 배포 시 `/dali-web/` 하위 경로의 Wasm·Worker·리소스 URL을 검증합니다.

## 단계별 주요 판단

1. P1: 단일 스레드 실험과 Worker 기반 실행을 비교합니다. 최초 테스트가 단일 스레드였다는 이유로 생산 구조를 확정하지 않습니다. 이벤트 처리·업데이트·렌더·리소스 업로드의 소유자와 동기화를 정해야 합니다.
2. P2: `eglCopyBuffers`, `eglCreatePixmapSurface`, `glBlendBarrier`는 현재 조사된 미해결 심볼입니다. 전체 렌더러에서는 추가 의존성이 나타날 수 있습니다. 미지원 기능을 무조건 빈 함수로 처리하지 않습니다. 버퍼 업로드는 D2에 따라 별도 웹 구현과 버퍼 소유 CPU shadow로 필요한 부분 쓰기 보존을 구현합니다. native Memory2/3 경로는 유지하며 FULL_ES3를 데이터 보존 해결책으로 채택하지 않습니다. 셰이더 바이너리는 웹에서 사용하지 않는 경로를 마련합니다.
3. P3: Core 테스트의 모의 Graphics Controller를 생산 GLES 렌더러 대신 사용하지 않습니다. 직접 WebGL로 도형만 그려 놓고 DALi 렌더링으로 판정하지 않습니다.
4. P4: 브라우저 프레임 콜백과 시간 처리를 연결합니다. 클릭은 DOM에서 DALi 입력까지 이어져야 합니다. 화면 변화와 DALi 속성 변화 모두 확인합니다.
5. P5: FreeType·HarfBuzz 등 재사용 범위, 폰트 탐색, 다운로드·파일 접근을 분리합니다. IME 입력은 단순 텍스트 표시와 별도 기능이며 지원 범위를 명시합니다.
6. P7: 제안 검증 행렬은 Ubuntu Firefox·Chromium, Windows Chrome·Edge입니다. 실제 기기 접근이 없으면 해당 항목은 미검증으로 남깁니다. 실행 크기·초기 로딩·프레임 시간은 측정 후 목표를 정합니다. 기존 네이티브 경로를 수정했다면 해당 회귀 검증도 포함합니다.
7. P8·P9: 임의 C++ 빌드는 별도 격리 환경과 자원 제한이 필요합니다. iframe만으로 무한 루프 중단이 보장된다고 가정하지 말고 Worker 또는 별도 실행 구조를 검증합니다. 공개 배포·계정 연동은 별도 실행 범위입니다.

## context를 옮기는 기준

상위 표는 마일스톤이며, context는 아래 하위 작업 단위로 나눕니다. 한 단계에 여러 대화가 필요하면 `P3-a 초기화`, `P3-b 픽셀 검증`처럼 좁히되, 다음 대화가 사용할 산출물이나 진단 결과가 남는 지점에서 전환합니다. 하루 또는 수정 파일 수로 기계적으로 나누지 않습니다.

1. 전환하기 좋은 시점: 링크 성공, 픽셀 검사 통과, 실패 원인이 재현 코드로 좁혀짐, 설계 결정 확정 직후.
2. 피할 시점: 여러 가설을 동시에 수정 중인데 diff·로그가 정리되지 않은 상태, 장시간 빌드나 서버의 소유권이 불명확한 상태.
3. context가 먼저 부족해지면 완료를 주장하지 않고 중간 상태를 저장합니다. 재현 명령, 마지막 오류, 시도한 대안, 다음 한 가지 행동을 남깁니다.
4. 새 대화의 필수 읽기는 README·STATE·HANDOFF와 PLAN의 해당 단계입니다. 전체 대화, SDK 소스, 모든 로그를 한꺼번에 읽지 않습니다.
5. 권장 이동 순서는 `R1-a → R1-b → R2-a → R2-b → P1 → P2 이후의 검증 단위`입니다. R1은 저장소 구조만, R2는 경로 이관과 기존 결과 재현만 다룹니다. 렌더러 신규 구현은 P1 이후로 분리합니다.
6. D1은 배포 설정과 실제 URL 검증을 별도 context에서 수행합니다. 이후 단계는 아래 분할 후보를 직전 단계 결과에 맞춰 구체화합니다.
7. R1에서 원본 선택이 막히면 후보 URL·SHA·차이를 남깁니다. R2 완료 인수인계에는 새 작업 루트, 새 repo commit, 재현 명령, 이전 로그 위치와 미이관 항목을 반드시 기록합니다.
8. 복잡한 단계가 2개 이상 섞이면 context를 나눕니다. 예를 들어 P2 링크 문제와 P5 폰트 포팅을 함께 시작하지 않습니다.

### 바로 적용할 context 단위

R1-a·R1-b·R2-a·R2-b 및 상위 R1·R2는 완료했습니다. P1은 설계 초안·소규모 SDK guard 검사를 마쳤으나 D3~D4 미결로 완료하지 않았습니다. P2 이후는 미착수입니다. [R2-a 결과](archive/probe/docs/R2-a-RESULTS.md)에 새 Core 검증과 인수인계를 기록했습니다. [R2-b 결과](R2-b-RESULTS.md)에 재검증과 기록 전환을 기록했습니다. [R1-b 결과](archive/probe/docs/R1-b-RESULTS.md)에 commit·push·검증 증거를 기록했습니다.

| 단위 | 목표 | 완료 및 인수인계 조건 |
|---|---|---|
| R1-a 완료 | 원본 URL·기준 SHA·squash 정책 선정 | 세 원본의 접근 가능성 및 commit 존재 확인, P0 기준과의 차이 기록, import 정책과 파일 목록 확정. subtree import는 다음 단위로 넘김 |
| R1-b 완료 | repo 뼈대·subtree 구성 | R1-a 결정을 적용하고 lock·remote 준비 스크립트·라이선스·제외 규칙 확인. 별도 로컬 clone으로 세 소스 포함 검증. 실제 commit과 push 여부 기록 |
| R2-a 완료 | 빌드·실험 코드 경로 이관 | 새 경로에서 Core 빌드·Node 검사 통과. 기존 결과 보존과 변경 파일 기록. R2-a 당시 기록 기준은 기존 공간 유지, R2-b에서 전환 완료 |
| R2-b 완료 | 브라우저 검증과 기록 기준 전환 | Firefox·GL 탐색 결과 비교, 문서 링크 점검, 새 repo docs를 기준으로 전환하고 기존 문서에 안내. 다음 시작점은 P1 |

### 이후 단계의 분할 후보

| 단계 | 권장 분할 |
|---|---|
| P1 | 실행 계약 설계 한 단위. 스레드·호스팅 실험이 커지면 독립 단위로 분리 |
| P2 | 최소 렌더러 링크 대상·의존성 진단 → 확인된 호환성 수정·전체 대상 링크 검증 |
| P3 | 컨텍스트·표면 초기화와 해제 검증 → DALi 도형·실제 픽셀 검사 |
| P4 | 프레임 루프·애니메이션 → 입력·리사이즈 → 반복 실행·해제 |
| P5 | 리소스 로딩·이미지 → 폰트 의존성·텍스트 표시 |
| P6 | foundation·레이아웃 → 선택한 components |
| P7 | 재현 빌드 → 브라우저·OS 검증 → 수명·메모리·복구 검증 |
| P8 | SDK 패키징·버전 계약 → 격리된 컴파일 API |
| P9 | 편집·오류·로그 연결 → 실행 격리·중단·재실행 |
| D1 | 기본 Pages 배포와 실제 URL 검증을 한 단위로 유지 |

각 단위에서 구현과 기본 검증은 함께 끝냅니다. 오류 하나마다 context를 바꾸지 않고 같은 원인을 좁히는 조사는 이어갑니다. 성능 측정은 해당 기능 검증에 포함하되 병목 개선이 커지면 독립 단위를 만듭니다. 후보 분할은 일정 확약이나 자동 실행 지시가 아닙니다.

## 성능 검증 계획

현재 Debug·모의 그래픽 테스트는 성능 근거로 사용하지 않습니다. 브라우저가 무조건 많이 느리다고 보거나, 네이티브 대비 일정 비율의 성능을 미리 보장하지 않습니다.

1. P3: 실제 픽셀 확인 후 최적화 빌드의 첫 측정 기준을 남깁니다. P4에서 Actor·draw call 수를 늘리는 애니메이션 장면으로 확장합니다.
2. 동일 장치·동일 장면·픽셀 해상도·배율에서 네이티브와 웹을 비교합니다. GPU 가속 여부와 브라우저·SDK·revision·최적화 옵션을 기록합니다. 헤드리스 소프트웨어 렌더링 수치를 사용자 GPU 성능으로 해석하지 않습니다.
3. 다운로드·Wasm 초기화·셰이더 준비·첫 프레임 시간과, 준비 후 연속 프레임 성능을 분리합니다. P8에서는 서버 대기·C++ 컴파일·링크 시간도 별도로 측정합니다.
4. 평균 FPS만 보지 않고 프레임 간격의 중앙값·p95·p99, 긴 프레임과 입력 응답을 확인합니다. CPU 업데이트·GL 제출 시간과 GPU 시간은 가능한 측정 도구로 구분하며 동기화로 측정을 왜곡하지 않습니다.
5. 60Hz 환경의 초기 예제 목표는 60fps에 맞는 약 16.7ms 프레임 예산입니다. 달성 여부는 측정으로 판정하고, 대상 장치·장면·브라우저를 함께 명시합니다. 현재 달성한 결과가 아닙니다.
6. GL 호출·상태 변경, 매 프레임 버퍼/텍스처 업로드, FULL_ES3 에뮬레이션, 스레드 통신·동기화를 우선 진단합니다. P5·P6에서는 폰트 최초 로딩·glyph 생성·텍스트 갱신도 구분합니다.
7. P3·P4에서 병목이 확인되면 UI 기능을 넓히기 전에 원인과 수정 범위를 판단합니다. 정상 동작하는 경로를 확보하기 전에 추측만으로 최적화하지 않습니다.

근거: [Emscripten WebGL 최적화 문서](https://emscripten.org/docs/optimizing/Optimizing-WebGL.html)는 네이티브 대비 GL 호출 검증 비용과 에뮬레이션 비용을 설명합니다. 실제 DALi 손실률은 아직 측정하지 않았습니다.

## 예상 규모 갱신

기존 예상은 PoC 1~3주, 기본 UI 4~8주, 플레이그라운드 2~4개월의 누적 범위였습니다. Core의 초기 장애는 줄었지만 생산 렌더러 실행과 스레드는 미검증이므로 기간을 단축해서 확정하지 않습니다. P3의 실제 픽셀 검증 후 PoC 잔여량, P6 이후 제품화 잔여량을 다시 산정합니다. context 수는 작업 기간과 같지 않습니다.

## 계획 변경 규칙

기술 결과로 선행 관계나 범위가 바뀌면 이 표와 STATE를 함께 수정하고, 이유와 근거를 JOURNAL에 남깁니다. 사용자와 합의한 구조를 바꿔야 한다면 먼저 영향과 대안을 설명합니다. 사용자가 특이 사항에서 중단을 지시한 경우 그 지시를 우선합니다.
